# リーンキャンバス作成・仮説検証設計

事業アイデアを1枚のキャンバスに構造化し、「最初に潰すべきリスク」を特定して検証計画につなげるスキル。

## 大原則

**キャンバスは書類ではなく仮説の一覧表。** 埋めることが目的ではなく、どのマスが未検証の当て推量かを可視化し、検証の順番を決めるために書く。全マスに [事実] / [仮説] のラベルを付ける。

## 手順

### 1. 形式の選択

- **リーンキャンバス**: 新規事業・スタートアップ向け（課題起点）。基本はこちら
- **ビジネスモデルキャンバス（BMC）**: 既存事業の構造整理・パートナー関係が複雑な事業向け

### 2. リーンキャンバスの記入（この順番で）

順番に意味がある。課題と顧客から始め、ソリューションは後:

1. **課題**: 上位3つ。顧客の言葉で書く。+既存の代替手段（「何もしない」も代替手段）
2. **顧客セグメント**: 誰の課題か。特に**アーリーアダプター**（最初に金を払うほど困っている人）を具体化する
3. **独自の価値提案 (UVP)**: 「なぜ既存の代替手段でなくこれか」を1文で。機能でなく結果で書く
4. **ソリューション**: 課題それぞれに対応する最小限の解決策（3つ）
5. **チャネル**: アーリーアダプターに実際に届く経路（今日から使えるものを優先）
6. **収益の流れ**: 誰がいくら払うか。価格の初期仮説を必ず数字で（`pricing-strategy` で深掘り可）
7. **コスト構造**: 主要コストと、ざっくりの損益分岐（`financial-model` で精緻化）
8. **主要指標**: 事業が動いている証拠となる数字（`growth-metrics` のAARRRと接続）
9. **圧倒的優位性**: 真似できない理由（なければ「現時点でなし」と正直に書く。多くの初期事業はなしで正常）

### 3. 危険な仮説の特定

キャンバス全体を見て、**「これが間違っていたら事業が成立しない」仮説**をランク付けする。典型的な順序:

1. 課題仮説: その課題は本当に存在し、深刻か（大抵これが最初）
2. 顧客仮説: アーリーアダプターは特定・到達できるか
3. 価値仮説: 解決策に金を払うか（欲しい≠買う）
4. 成長仮説: 採算の合うコストで顧客を増やせるか

### 4. 検証実験の設計

最重要仮説に対して、**作らずに検証する方法**から順に検討する:

- 課題インタビュー（5〜10人。過去の行動を聞く。ソリューションの説明はしない）
- LP+事前登録 / プレオーダー（お金 or メールアドレスという実コストを払うか）
- コンシェルジュMVP（手作業で価値を提供してみる）/ プロトタイプ

実験ごとに: 検証する仮説 / 方法 / **事前に決める判断基準**（「10人中4人が◯◯なら前進」）/ 期限。基準を後決めにすると都合よく解釈するため必ず事前に。

### 5. 運用

キャンバスは `docs/lean-canvas.md` 等に保存し、検証のたびに更新する（変更履歴を残す）。検証結果が仮説を否定したら、ピボットの選択肢（顧客を変える / 課題を変える / 解決策を変える）を整理して提示する。

## 注意事項

- アイデアの否定材料が出たら率直に伝える。ただし「仮説が死んだ」ことと「事業が死んだ」ことは違う — 学びとして次の仮説を示す
- ソリューション先行の依頼（作りたい物が先にある）でも、課題と顧客のマスを埋めさせる方向に誘導する
- 市場規模の裏付けが必要になったら `market-research` を使う
