# ゲームローカライズ

ゲームの多言語対応を、後から破綻しない形で設計・実装・レビューするスキル。

## 手順

### 1. 現状診断

コードとデータを走査して、ローカライズ阻害要因を洗い出す:

- [ ] ハードコードされた表示文字列（コード内リテラル）の分布
- [ ] 文字列連結で文を組み立てている箇所（`"Get " + item + "!"` — 語順が言語で変わるため翻訳不能）
- [ ] 画像に焼き込まれたテキスト（ロゴ・ボタン・看板）
- [ ] 数値・日付・通貨のフォーマット処理
- [ ] フォントの文字カバレッジ（対象言語のグリフを持つか。日本語→英語は楽だが、逆や中韓・キリル対応はフォント選定が先）

結果を「対応済み / 要修正 / 要判断」で一覧化して報告する。

### 2. 基盤の設計・実装

**テキストの外部化**
- 全表示文字列をキー付きデータ（JSON / CSV / gettext PO / エンジン標準の仕組み）に出す
- キーは位置ベース（`title_button_3`）ではなく意味ベース（`menu.start_game`）で命名する
- エンジン標準があればそれを使う（Unity: Localization パッケージ、Godot: TranslationServer/CSV、Web: i18next 等）。自作は最終手段

**翻訳可能な構造にする**
- 文字列連結を撤廃し、プレースホルダー方式に: `「{item}を手に入れた！」` — 語順の変更は翻訳側で吸収できる
- 複数形・性数一致は ICU MessageFormat 等の plural 対応形式を使う（英語は 1/その他、ロシア語は3分類など言語で規則が違う）
- 話者の性別・敬語で変わるセリフは、キーを分けるかメタデータを持たせる

**翻訳ワークフロー**
- 翻訳者に渡すファイルに**文脈情報**（どの画面・誰のセリフ・文字数制限）の列を必ず付ける。文脈なし翻訳は品質が出ない
- 用語集（`/game-narrative` の glossary）を訳語対応表に拡張する
- 未翻訳キーの検出スクリプト（全言語ファイルのキー差分）を用意する

### 3. レイアウト・表示のレビュー

言語切り替えで壊れる箇所を検出する:

- **伸長**: 英語→ドイツ語は 1.3〜2 倍に伸びる。日本語→英語も伸びる。固定幅ボタン・1行表示のはみ出し箇所を特定する（自動折り返し・自動縮小・スクロールのどれで受けるか提案）
- **フォールバック**: 未翻訳キーの表示（キー名が出る? 原語が出る?）を明示的に設計する
- **禁則処理**: 日本語の行頭句読点、単語分かち書きしない言語の折り返し
- テスト用に**擬似ローカライズ**（全文字列を `[!!! Ｗｏｒｄ ｅｘｐａｎｄｅｄ !!!]` 風に変換する言語）を追加し、焼き込み文字列とレイアウト崩れを一括検出する方法を提案する

### 4. 文化面の確認

- 対象地域で問題になりうる表現（宗教的シンボル、手のジェスチャー、歴史・地図の扱い）に気づいたら指摘する
- レーティング（CERO / ESRB / PEGI）の基準差で対応が変わる表現（飲酒・ギャンブル等）を指摘する

## 注意事項

- 「あとで対応」が最も高くつく領域。プロジェクト初期なら、翻訳はしなくても**外部化だけは今やる**ことを強く推奨する
- 機械翻訳で仮埋めする場合は、仮であることをデータ上でマークする（`"_mt": true` 等）
- 実装変更後は必ず全言語でキー欠落チェックを実行する
