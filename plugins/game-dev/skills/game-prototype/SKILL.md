# ゲームプロトタイプ作成

アイデアやコンセプトを「今すぐ遊べる形」にするスキル。目的は**コアループが面白いかを最小コストで検証すること**。見た目・拡張性・コード品質はすべて後回し。

## 手順

### 1. 技術選定

既存プロジェクトがあればそのエンジン・言語に従う。ゼロからの場合のデフォルト:

- **第一候補: 単一 HTML ファイル**（Canvas 2D + vanilla JS）。ブラウザで開くだけで遊べ、共有も一瞬。外部依存なし
- 3D が必須なら Three.js、物理が本質なら Matter.js 等を検討（ただし本当に必須か疑う。3D のアイデアも 2D 見下ろしで検証できることが多い）
- ユーザーが Unity / Godot / Pygame 等を使っている場合はそれに合わせる

### 2. スコープの切り詰め

実装前に「検証したい問い」を1文で定義し、ユーザーに宣言する。
例:「重力反転で地形を進むのは気持ちいいか?」

その問いに不要なものはすべて省く:
- タイトル画面・メニュー → 不要（即ゲーム開始）
- セーブ・設定 → 不要
- 複数レベル → 1面で十分
- アート → 図形と色で表現（`/placeholder-assets` 参照）
- 音 → 検証に効く場合のみ Web Audio のビープで

### 3. 実装

- **最初の30分で「操作できて何かが起きる」状態**を作り、そこから積む
- ゲームループは固定タイムステップまたは deltaTime ベースで書く（フレームレート依存の挙動は調整不能になるため、プロトタイプでもここだけは守る）
- 調整パラメータ（速度・重力・クールダウン等）はファイル冒頭の `CONFIG` オブジェクトに集約する — バランス調整の反復が速くなる
- デバッグ表示（座標・状態・FPS）をキー1つでトグルできるようにする
- 入力はキーボード基本。モバイル前提のアイデアならタッチ対応

### 4. 動作確認

- 完成したら自分でコードを読み直し、ゲームオーバー→リスタート、境界値（画面端・0体力）の挙動を確認する
- ブラウザ実行環境があれば実際に開いて確認する。なければユーザーに開き方を1行で伝える（`open index.html` 等）

### 5. 引き渡し

完了時に以下を伝える:

- 操作方法（1〜3行）
- 検証したい問いと、どこに注目して遊んでほしいか
- CONFIG のどの値をいじると手触りが変わるか（ユーザー自身で調整の実験ができるように）

## 反復

プロトタイプは1回で終わらない。フィードバックを受けたら:

- 「面白くない」→ 原因の仮説を2〜3案出し、一番安い変更から試す
- 「もっと機能を」→ コアが面白いと確認できるまで機能追加を warning 付きで受ける（コアがつまらないまま盛るのは無駄になりやすい）
- コアが確認できたら、本実装への移行（エンジン選定・設計）を `/game-design-doc` と合わせて提案する

## 注意事項

- プロトタイプのコードを本実装に流用しない前提で書く（その旨をユーザーにも伝える）
- ただし「捨てる前提」を言い訳に動かないものを出さない。**遊べることが唯一の品質基準**
- 1ファイル・500行を超えそうなら、スコープが「プロトタイプ」を超えている。分割やスコープ縮小をユーザーに相談する
