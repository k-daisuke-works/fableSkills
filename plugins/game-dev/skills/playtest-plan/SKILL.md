# プレイテスト計画・ゲームQA

プレイテストの設計と、ゲーム特有の QA を行うスキル。「動くか」のテストと「面白いか」のテストは別物として扱う。

## モードの判別

- **QA（動くかのテスト）**: バグ・進行不能・エッジケースを探す → §1
- **プレイテスト（面白いかのテスト）**: 人に遊ばせて体験を検証する → §2

依頼がどちらか不明なら両方の観点で薄く始めるのではなく、確認する。

## §1. ゲームQA

### テスト観点表の作成

ゲームの機能一覧（GDD・コード）から観点表を作る。ゲーム特有の頻出バグ領域:

**進行・状態**
- [ ] 進行不能: 必須アイテム入手前に扉を閉める、イベント中のセーブ&ロード、フラグの順序前後
- [ ] セーブ/ロード: あらゆる状態（戦闘中・演出中・メニュー中）でのセーブ→ロードで整合するか
- [ ] ポーズ: 演出・物理・タイマー・音がすべて正しく止まる/再開するか

**境界・異常系**
- [ ] 所持金・所持数の 0 / 上限 / 上限+1（カンスト・オーバーフロー）
- [ ] 画面端・マップ外・コリジョンの隙間（壁抜け・奈落）
- [ ] 連打・同時押し・操作の高速切り替え（ステート遷移の隙間を突く）
- [ ] 想定外の順序（ボスを先に倒す、会話を途中でキャンセル、購入画面で所持金を使い切る）

**環境**
- [ ] 解像度・アスペクト比・ウィンドウリサイズ、フレームレート差（30/60/144fps・低速環境）でロジックが変わらないか
- [ ] 入力デバイス（キーボード/パッド/タッチ）の切り替え・抜き差し
- [ ] 中断・復帰（モバイルのバックグラウンド、スリープ）

### 実施

- コードを読んで疑わしい箇所（時間依存・フラグ管理・状態遷移）を特定し、観点を追加する
- 自動テストが書ける観点（セーブデータの整合、数値の境界）はテストコードとして書くことを提案する
- 発見したバグは再現手順・期待/実際・頻度（毎回/稀）・重大度（進行不能>データ破壊>表示>軽微）で報告する

## §2. プレイテスト計画

### 計画の作成

```markdown
# プレイテスト計画

**検証したい問い**（3つまで。全部を一度に検証しない）:
例:「チュートリアルなしで基本操作に気づけるか」

**参加者**: 人数・属性（ターゲット層か、ゲーム経験）
**形式**: 対面観察 / リモート / 配布アンケート
**セッション**: 所要時間、どこからどこまで遊ばせるか
**観察者の禁止事項**: 操作を教えない・言い訳しない・質問に質問で返す
```

### 観察シートとアンケート

- 観察シート: 検証したい問いごとに「観察すべき行動」を具体化する（「迷った」ではなく「30秒以上同じ場所で入力が止まった回数」）
- アンケートは行動の後で: 「楽しかったですか」（はい、と答えがち）ではなく「もう一度遊びたいか」「友人に勧めるか」「一番イライラした瞬間はどこか」を聞く
- 定番の計測: 各レベルの離脱率・死亡回数・所要時間。テレメトリ（ログ収集）の実装も提案できる

### 結果の分析

- 「プレイヤーの言うこと」より「プレイヤーがしたこと」を優先する
- 指摘の頻度で優先度をつける。1人だけの意見は保留リストへ
- 修正案は問題ごとに複数出し、最小の変更を推す（プレイヤーの提案する解決策をそのまま実装しない — 問題は本物、解決策は疑う）

## 注意事項

- 開発者自身のプレイは「上手すぎて」難易度検証にならないことを常に注記する
- QA で見つけた重大バグ（進行不能・データ破壊）は他の報告に埋もれさせず最初に報告する
