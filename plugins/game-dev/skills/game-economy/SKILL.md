# ゲーム内経済設計

通貨・アイテム・報酬の流れを設計し、シミュレーションで健全性を検証するスキル。

## 大原則

**経済は「蛇口(source)と排水口(sink)」の収支で考える。** 獲得手段の合計と消費手段の合計を時間軸で見て、意図した速度で資産が推移するかを検証する。片方だけ設計された経済は必ずインフレかデフレで破綻する。

## 手順

### 1. 経済マップの作成

まず全体像を1枚にする。既存ゲームならコード・データから拾い、新規なら設計する:

```markdown
| 通貨/資源 | Source（獲得） | 獲得レート | Sink（消費） | 消費レート |
|---|---|---|---|---|
| ゴールド | 戦闘/クエスト/売却 | X/時 | 装備購入/強化/修理 | Y/時 |
```

- 複数通貨がある場合は、通貨間の交換経路と、各通貨の役割（ソフトカレンシー/ハードカレンシー/専用トークン）を明記する
- **無限source×有限sink**（例: 敵は無限に湧くが買うものが尽きる）の組み合わせを検出する — 長期インフレの典型原因

### 2. プレイヤー時間軸での検証

体験目標を決めてからシミュレーションする:

- 「初めての大きな買い物（例: 上位装備）まで X 時間」「常に収入の Y% 程度は使い道がある」等
- 想定プレイヤー（カジュアル/コア、無課金/課金）ごとに1セッション・1日・1週間の収支を計算するスクリプトを書く
- 進行に伴う獲得レート上昇（後半の敵ほど落とす）とシンクの価格曲線が釣り合っているか確認する

### 3. 確率報酬（ドロップ・ガチャ）の設計

期待値だけでなく**分布と最悪ケース**で設計する:

- 「ドロップ率3%」→ 100回で出ない確率は約4.8%。`(1-p)^n` で「N回試行して出ない確率」を必ず併記する
- 目標を「平均 X 回で入手」ではなく「95% のプレイヤーが Y 回以内に入手」で設定する
- 最悪ケースを抑える仕組みを検討する: 天井（上限保証）、疑似乱数（PRD: 失敗ごとに確率上昇）、パリティ（重複排除）
- ガチャの場合、日本の慣行（提供割合の表示、コンプガチャ禁止）と主要プラットフォームの規約（Apple/Google はルートボックスの確率開示必須）に触れる設計になっていないか確認する
- シミュレーション: 1万人分の引きをモンテカルロし、入手までの試行回数の分位点（50%/95%/99%）と課金額換算を出す

### 4. 運用時の健全性チェック（既存ゲームのレビュー）

- 最効率ファーミング経路を探す（プレイヤーは必ず見つける）。想定獲得レートの何倍かを計算し、意図の範囲か判定する
- 交換経路を辿って無限増殖・裁定取引（AをBに変えてまたAに戻すと増える）がないか確認する
- トレード機能がある場合、RMT・BOT の影響を受けやすいポイントを指摘する

## 報告形式

- 経済マップ（表）
- シミュレーション結果（時間軸の資産推移、確率の分位点）
- 問題点と修正案（どのレート・価格をいくつに変えるか、根拠付き）

## 注意事項

- マネタイズ設計を伴う場合、エンゲージメントを損なう搾取的パターン（意図的な不便の販売、疑似通貨による価格の不透明化の悪用）はリスクとして正直に指摘する
- 数値は必ずデータファイル化を提案する（運用調整がコード変更なしでできるように）
- シミュレーションコードはスクラッチパッドではなくリポジトリ（`tools/economy-sim/` 等）に残すことを提案する。運用中ずっと使うため
