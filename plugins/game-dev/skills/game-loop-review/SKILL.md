# ゲームループ・パフォーマンスレビュー

ゲーム特有のパフォーマンス問題（毎フレーム実行されるコードの負荷、GC スパイク、描画ボトルネック）を特定・修正するスキル。

## 大原則

**推測で最適化しない。** 症状の聞き取りと計測を先に行い、証拠のある箇所だけ直す。「なんとなく遅そうなコード」の書き換えは、効果がない上にバグを入れる。

## 手順

### 1. 症状の分類

まず症状を特定する（ユーザーの訴えかプロファイルから）:

- **恒常的な低FPS** → 毎フレームの処理が予算超過。更新か描画かを切り分ける
- **周期的なカクつき（スタッター）** → GC・アセット遅延ロード・定期処理のスパイクを疑う
- **時間経過で悪化** → リーク（オブジェクト・イベントリスナー・エンティティの解放漏れ）を疑う
- **特定の状況でのみ発生** → その状況で増える処理（敵数・パーティクル・当たり判定ペア数）を疑う

### 2. 計測

環境に応じた計測手段を使う・提案する:

- ブラウザ: Performance タブのプロファイル、`performance.now()` での区間計測コードの挿入
- Unity: Profiler、Frame Debugger
- Godot: モニタ、プロファイラ
- 計測できない環境なら、区間計測ログを仕込んだビルドをユーザーに実行してもらう

フレーム予算の目安: 60fps = 16.6ms、30fps = 33.3ms。更新+描画+その他がこれに収まるか。

### 3. コードレビュー観点

計測で当たりをつけた領域を、以下の頻出パターンで確認する:

**毎フレームのアロケーション（GCスパイクの主因）**
- update/draw 内での `new`、配列・文字列・クロージャ生成、LINQ/map/filter チェーン
- 対策: オブジェクトプール、事前確保バッファの再利用、文字列連結の排除

**計算量の爆発**
- 全対全の当たり判定（N²）→ 空間分割（グリッド・quadtree）や broad phase の導入
- 毎フレームの全エンティティ走査で、大半が「何もしない」→ 状態別リスト・スリープ機構
- 毎フレームの `find` / `GetComponent` / セレクタ検索 → 参照のキャッシュ

**描画**
- ドローコール数（スプライトのバッチング・アトラス化で削減）
- 画面外オブジェクトの描画（カリングの有無）
- 毎フレームの Canvas 状態変更・シェーダ切り替え・テクスチャバインド
- 全画面再描画 vs ダーティ矩形（2Dの場合）

**構造問題**
- 可変タイムステップで物理・ゲームロジックが動いている（挙動が環境依存になる）→ 固定タイムステップ+補間
- update 内の同期 I/O・重い文字列処理・ログ出力

### 4. 修正と検証

- 修正は1つずつ適用し、それぞれ計測値の前後比較を取る（まとめて直すとどれが効いたか分からない）
- 挙動が変わっていないことを確認する（最適化でゲームプレイが変わるのは不具合）
- 結果は「修正内容 / 修正前→修正後の計測値 / 残る課題」で報告する

## 注意事項

- 可読性を大きく壊す最適化（手動インライン展開等）は、計測で効果が証明された場合のみ、コメント付きで行う
- 「プレイに影響が出ていない箇所」の最適化は提案に留める
- エンジンの機能（Unity の Job System、Godot の VisibleOnScreenNotifier 等）で解決できるものは自作より優先する
