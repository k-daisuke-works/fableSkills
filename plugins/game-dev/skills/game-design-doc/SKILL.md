# ゲームデザインドキュメント（GDD）

コンセプトを実装可能な仕様に落とし込む GDD を作成・保守するスキル。「読まれない分厚い文書」ではなく、**実装の判断に使われる生きた文書**を作る。

## 手順

### 1. 前提の確認

- 既存の企画書・コンセプトシート（`docs/concept.md` 等）があれば読み込む
- 既存の GDD があれば、新規作成ではなく更新・レビューとして扱う
- リポジトリにコードがあれば実装状況を確認し、GDD と実装の乖離を把握する

### 2. 構成

`docs/gdd/` 配下に分割して書く（1ファイル巨大文書は更新されなくなるため）:

```
docs/gdd/
├── 00-overview.md      # コンセプト・コアループ（concept.md の要約+リンク）
├── 01-mechanics.md     # コアメカニクスの詳細仕様
├── 02-controls.md      # 操作系・入力仕様
├── 03-progression.md   # 進行・成長・アンロック
├── 04-levels.md        # レベル/ステージ構成（詳細は /level-design へ）
├── 05-ui-ux.md         # 画面遷移・HUD・メニュー
├── 06-narrative.md     # 世界観・ストーリー（詳細は /game-narrative へ）
├── 07-audio-visual.md  # アート方向性・サウンド方針
├── 08-balance.md       # 数値設計の方針（詳細は /game-balance へ）
└── 09-tech.md          # 技術要件・対象スペック・エンジン
```

小規模プロジェクトでは 1〜3 ファイルに統合してよい。規模に合わせる。

### 3. メカニクス仕様の書き方

各メカニクスは以下のテンプレートで書く。**曖昧語（「気持ちよく」「適度に」）を数値・条件に置き換える**のがこのスキルの最重要ポイント:

```markdown
## <メカニクス名>

**目的**: このメカニクスがコアループのどこを支えるか
**トリガー**: いつ発動するか（入力・条件）
**挙動**: 何が起きるか。数値は仮でも必ず入れる（ジャンプ高さ 2.5m、クールダウン 3秒 等）
**フィードバック**: プレイヤーにどう伝わるか（エフェクト・音・UI）
**エッジケース**: 同時発動、連打、境界値での挙動
**未決事項**: 決まっていないことは「TBD」と明記（暗黙の未決が一番危険）
```

### 4. レビューモードの場合

既存 GDD のレビューを頼まれたら、以下の観点で指摘する:

- **曖昧さ**: 実装者が判断に迷う記述（数値なし・条件不明・「いい感じに」）
- **矛盾**: 文書間・文書内の食い違い
- **実装との乖離**: コードが既にある場合、GDD と実際の挙動の差分
- **抜け**: 失敗時・中断時・境界値の仕様がないメカニクス
- **スコープ**: MVP に不要な仕様が「必須」扱いになっていないか

### 5. 更新の場合

- 変更箇所だけでなく、影響を受ける他セクションも洗って更新する
- 大きな仕様変更は文書末尾に変更履歴（日付・変更内容・理由）を残す

## 注意事項

- GDD は「完成させる」ものではなく反復するもの。最初から全セクションを埋めようとせず、決まっていない箇所は TBD で残す
- 実装済みコードと矛盾する記述を見つけたら、どちらが正なのかユーザーに確認する（勝手にどちらかに合わせない）
- 数値はすべて「仮」と明記した上で必ず入れる。数値のない仕様は実装もバランス調整もできない
