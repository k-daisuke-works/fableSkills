## 仕様の正 (Source of Truth)

- 要件定義書: `<docs/requirements.md>` — **仕様の唯一の正。実装判断はすべてここに従う**
- 仕様が矛盾・欠落しているときの優先順位: **コンセプト > コアループ > 個別仕様**
- 仕様にない判断をしたら、その解釈を要件定義書に追記してから実装する(暗黙の仕様を作らない)
- 仕様の変更・追加はユーザーの承認を得てから。実装の都合で仕様を曲げない

## 開発ルール

1. **完成の定義**は要件定義書の受け入れ基準。必須機能がすべて動くまで「あれば嬉しい機能」に着手しない
2. **調整パラメータは `<CONFIGの場所(例: src/config.js)>` に集約。** 速度・時間・確率・HP等の数値をロジック内に直書きしない
3. **ゲームロジックはフレームレート非依存**(deltaTime または固定タイムステップ)。「1フレームあたりN」の書き方は禁止
4. **メカニクスはフィードバック込みで1機能。** エフェクト・音・画面反応のないメカニクス実装は未完成扱い
5. 機能を追加・変更したら、**ゲームオーバー→リトライの状態リセット**を必ず確認する(リセット漏れが最頻出バグ)
6. 数値バランスの変更は変更履歴(何を・いくつ→いくつ・なぜ)を `<docs/balance-log.md>` に残す

- 起動: `<例: ブラウザで index.html を開く / npm run dev>`

## エージェントの使い分け

game-dev プラグインのエージェントに以下の基準で委任する:

| 状況 | エージェント |
|---|---|
| 仕様の曖昧さ・矛盾に当たった / デザイン判断が必要 | `game-designer`(判断と仕様書更新。実装はしない) |
| 仕様が固まった機能の実装 | `gameplay-programmer`(1機能ずつ渡す) |
| 機能が一段落した / リリース前 | `qa-playtester`(壊しにいくテスト。修正はしない) |
| 数値の妥当性確認・調整案が欲しい | `balance-simulator`(シミュレーションで検証) |
| 重い・カクつく | `perf-profiler`(計測ファースト) |
| 仮素材が必要 / 見た目の底上げ | `asset-artist`(識別性優先の一括生成) |

運用ルール:
- 実装(gameplay-programmer)と検証(qa-playtester)は**別エージェント**に分ける。自分の実装を自分でOKにしない
- qa-playtester の報告するバグのうち、進行不能・データ破壊は他のタスクより優先して修正する
- balance-simulator の修正案は、適用前にユーザーに提示する

## スキルの使い分け(本体で作業する場合)
