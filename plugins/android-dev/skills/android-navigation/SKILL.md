# Androidナビゲーション

予測可能なバックスタックを持つ画面遷移を設計・実装するスキル。

## 大原則

**遷移図を先に描く。** 個々の遷移をその場しのぎで足すとバックスタックが破綻する（戻るたびに知らない画面が出る、二重画面、ログイン画面に戻れてしまう）。実装前に「画面一覧 + 遷移 + 各画面で戻るを押したらどこへ」をテキストで書き出し、それをコードに落とす。

## 手順

### 1. 遷移設計

```
[起動] → スプラッシュ判定 → (未ログイン) Login → Home
                          → (ログイン済) Home
Home → Detail(id) → Edit(id)
Home ⇄ Settings（ボトムナビ: 状態保存で切替）
戻る規則: Edit→Detail→Home→終了 / Login完了後はLoginをスタックから除去
```

- 「戻る」で戻ってはいけない画面（ログイン、完了画面、スプラッシュ）を必ず洗い出す → `popUpTo` の設計
- ボトムナビのタブ切替は「積む」のではなく `saveState/restoreState` 付きの切替にする

### 2. 実装（Navigation Compose）

- ルート定義は**型安全な方式**を採用する（現行の Navigation Compose は Serializable な data class/object でルートを定義できる。プロジェクトの既存方式があればそれに従う）
- **引数は ID など最小限のプリミティブを渡し、オブジェクトは渡さない**。遷移先が ID から Repository 経由で取得する（プロセス再生成・ディープリンクでも壊れない設計になる）
- NavController の操作（navigate/popBackStack）はルートの NavHost 周辺に集約し、個々の画面 Composable にはコールバック（`onNavigateToDetail: (Long) -> Unit`）として渡す — 画面の Preview・テスト可能性を守る
- 連打による二重遷移を防ぐ（現在地チェックか launchSingleTop）

### 3. ディープリンク（要件にある場合）

- URI パターンをルートに紐付け、**直接開かれても成立するか**を確認する（認証が必要な画面なら認証フローを経由して戻す設計）
- App Links（https スキーム）は `assetlinks.json` の配置検証まで手順に含める
- 通知タップからの遷移もディープリンクとして統一的に扱う（`android-notifications` と連携）

### 4. 検証

必ず動作確認する項目:

- [ ] 全遷移の順方向 + 各画面からの「戻る」（システムバックとアプリ内バックの両方）
- [ ] ログイン→完了後に戻ってもログイン画面が出ないこと
- [ ] タブ切替で各タブのスクロール位置・状態が保持されること
- [ ] 画面回転・プロセス再生成（開発者オプション「アクティビティを保持しない」）後の復帰
- [ ] ディープリンクからの直接起動と、そこからの「戻る」の着地点

## 予測型バックジェスチャー

Android 13+ の予測型バック（戻る先がプレビューされる）に対応するため、`OnBackPressed` の旧 API ではなく `BackHandler` / `PredictiveBackHandler` を使い、`enableOnBackInvokedCallback` の有効化を検討する（既存コードに旧 API があれば移行を提案）。

## 注意事項

- 「条件によって最初の画面を変える」はスプラッシュ/起動判定ルートで行い、NavHost の startDestination を動的に切り替えるハックをしない
- マルチモジュール構成では、feature モジュール間の直接参照を避けるため遷移のインターフェース化（コールバック集約 or ルート公開の規約）に従う
- 大画面・折りたたみ対応（リスト+詳細の2ペイン）が要件にあるなら、遷移設計の段階で組み込む（後付けは高くつく）
