# Androidテスト

速く・安定して・意味のあるテストを、適切な層に書くスキル。

## 大原則

**テストピラミッドを守る。** ロジックの検証は JVM 単体テスト（速い・安定）に寄せ、UIテストは「画面とユーザー操作の結合」だけに絞る。UIテストでビジネスロジックを検証し始めるとスイートが遅く不安定になり、やがて誰も走らせなくなる。

## 層別の書き方

### ViewModel・ドメインの単体テスト（最優先・最厚)

- 依存（Repository 等）はフェイク（手書きの偽実装）を基本にする。モックライブラリの verify 乱発は実装詳細への密結合を生む — 「状態がこうなる」を検証し「このメソッドが呼ばれた」の検証は最小限に
- **Coroutines**: `runTest` + `MainDispatcherRule`（TestDispatcher を Main に差す JUnit Rule。無ければ作る）。プロダクションコードは Dispatcher 注入になっていることが前提 — なっていなければ先に `android-architecture` の改善を提案
- **Flow/StateFlow**: 収集して値の遷移を検証する（Turbine 等の採用はプロジェクトに合わせる）。`stateIn` の SharingStarted による「購読までの初期値」に注意
- ViewModel に Android 依存が混ざってテスト不能な場合、テストを書く前に依存を切り出す（テストの書けなさは設計の警報）

### Repository・データ層

- Room: **インメモリDBで DAO を実テスト**（Robolectric or instrumented）。モックした DAO のテストはほぼ無意味
- Room マイグレーション: `MigrationTestHelper` でスキーマ履歴からの移行テスト（`android-data` のスキーマ管理が前提）
- API: MockWebServer で成功・4xx・5xx・タイムアウト・不正JSONの各応答に対するハンドリングを検証

### Compose UIテスト（薄く・要所だけ)

- `createComposeRule` で、ステートレスな Composable に UiState を直接流し込んでテストする（アプリ全体を起動しない)
- 検証対象を絞る: 状態→表示の分岐（ロード/エラー/空/通常）、主要操作→コールバック発火
- ノードの特定は `testTag` か セマンティクス。文字列リテラル依存はローカライズで壊れる
- 画面遷移を跨ぐ E2E は最重要フロー（ログイン→主要タスク完了）1〜2本まで

## 手順

1. **現状把握**: 既存テスト・テスト用の共通部品（Rule・フェイク・ビルダー）を確認し、流儀に合わせる
2. **対象の選定**: 依頼が漠然としていたら「バグると一番痛いロジック」（金額計算・状態遷移・同期処理）から優先する
3. **実装**: Given-When-Then を意識し、1テスト1検証。テスト名は「◯◯のとき△△になる」を日本語か英語でプロジェクトの慣習に合わせる
4. **実行**: `./gradlew test`（JVM）を必ず回す。instrumented test はエミュレータの有無を確認してから
5. **報告**: 追加したテストと**カバーされていない残りのリスク**をセットで報告する

## 不安定テスト（flaky）の対処

- `Thread.sleep` を使った待機は全部疑う → Idling 的な同期（Compose なら `waitUntil`、Coroutines なら TestScheduler）に置き換える
- 時刻・タイムゾーン・ロケール依存 → Clock を注入し固定する
- 実行順序依存（static / シングルトンの状態残り）→ setup/teardown でリセット
- 「リトライで通す」設定は原因の隠蔽。最後の手段にする

## 注意事項

- カバレッジ率を目的化しない。数字が必要な場合も「重要ロジックの分岐カバー」を優先する
- スクリーンショットテストの導入はチームの運用（差分承認フロー）が回るかを確認してから提案する
- CI での実行（`android-ci` スキル）とセットで初めて価値が出る。ローカルでしか動かないテスト設定を作らない
