# Android通知

ユーザーに切られない通知設計と、確実に届く実装を行うスキル。

## 大原則

**通知はユーザーの注意の借金。** 価値のない通知はアプリごと通知オフ→アンインストールに直結する。実装の前に「この通知はユーザーにとって何の価値か」「頻度はどれくらいか」を確認し、価値が説明できない通知は実装前に指摘する。

## 手順

### 1. 通知設計

- 通知の種類を洗い出し、**チャンネル**に分類する（ユーザーは種類別にオフにできる。「その他」1個の設計はユーザーから調整手段を奪う）
- チャンネルごとに重要度（IMPORTANCE_*）を設定する。全部 HIGH にしない — 本当に割り込むべきものだけ
- タップ時の着地画面と、そこからの「戻る」の挙動を決める（`android-navigation` のディープリンク設計と統一）

### 2. 実装の要点

**権限（Android 13+）**
- `POST_NOTIFICATIONS` はランタイム権限。**文脈のあるタイミング**で要求する（起動直後の即ダイアログは拒否率が高い。「リマインダーを設定した直後」など価値が明確な瞬間に）
- 拒否された場合の動線（機能は動くが通知は来ない旨の表示、設定画面への誘導）まで実装する
- 通知チャンネルがOS設定でオフにされているケースも `areNotificationsEnabled()` / チャンネル状態で検知し、必要な箇所で案内する

**表示**
- 通知は更新・キャンセルまで管理する（完了した処理の進捗通知が残り続けるのは頻出バグ。ID 管理を設計する）
- 同種の複数通知はグループ化（サマリー通知）する
- アイコンはモノクロのシルエット（カラーアイコンは白い四角になる）

**タップ遷移**
- PendingIntent は immutable フラグ + ディープリンク経由で。「アプリが死んでいる状態からのタップ」で正しい画面+正しいバックスタックになるかが品質の分かれ目

### 3. FCM（プッシュ通知が要件の場合）

- 通知メッセージ（自動表示・カスタム性低）とデータメッセージ（onMessageReceived で自前処理・確実性は下がる）の違いを理解して選ぶ。挙動がフォアグラウンド/バックグラウンドで変わる点を必ずテストする
- トークンのライフサイクル（初回取得・ローテーション・サーバーへの登録/失効）を実装する
- サーバー側の送信要件（HTTP v1 API・サービスアカウント）はサーバー担当と分担を確認する
- 多端末・再インストール・通知オフ端末への送信失敗をサーバー側でハンドリングする前提を共有する

### 4. 検証

- [ ] アプリがフォアグラウンド / バックグラウンド / キル状態それぞれでの受信と表示
- [ ] 通知タップからの遷移（キル状態から含む）と、そこからの「戻る」
- [ ] 権限拒否状態・チャンネルオフ状態での挙動（クラッシュせず、適切に案内）
- [ ] Doze 中の受信遅延の確認（FCM の優先度設定）
- [ ] 通知の消し忘れ（処理完了後・ログアウト後に残らないか）

## 注意事項

- マーケティング通知を実装する場合、オプトアウト手段の実装と頻度の節度を必ず添える（`marketing-biz` 系の施策でも通知の切られやすさは共有する)
- スケジュール通知（リマインダー）は AlarmManager の正確なアラーム権限（`SCHEDULE_EXACT_ALARM`）の要件が変わりやすい領域。最新の制約を確認してから設計する
- 通知に個人情報を出しすぎない（ロック画面に表示される前提で内容を設計し、`setVisibility` を検討する）
