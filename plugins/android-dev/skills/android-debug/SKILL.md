# Androidデバッグ・トラブルシューティング

エラーを場当たりでなく、証拠から系統的に潰すスキル。

## 大原則

**エラーメッセージを最後まで読む。** Gradle・Kotlin・実行時エラーは、最初に目に付く行ではなく「Caused by」の最深部に真因があることが多い。推測で設定をいじり回す前に、ログ全文の取得と読解に時間を使う。**一度に変えるのは1つ**、変更のたびに再現確認する。

## ビルドエラー

### 情報収集

- `./gradlew assembleDebug --stacktrace`（必要なら `--info`）で全文を取得。最深の `Caused by` を特定する
- 直前に何を変えたか（依存追加・AGP更新・ファイル追加）を git diff で確認する — ビルドエラーの大半は直前の変更起因

### 頻出パターンと対処

- **バージョン非互換**（AGP ⇔ Gradle ⇔ Kotlin ⇔ JDK）: 公式の互換表を確認する。エラーに「requires」「was compiled with」が出たらまずこれ。闇雲な上げ下げをせず、互換表で整合する組を選ぶ
- **依存の重複・競合**: `./gradlew :app:dependencies` で依存ツリーを出し、どの経路で競合版が入るかを特定してから resolutionStrategy や BOM で揃える（`exclude` 乱発は最後の手段）
- **KSP/kapt エラー**（Room・Hilt）: 生成コードのエラーは元アノテーションの誤りが原因。生成失敗の1つ上のログに実際の指摘がある
- **キャッシュ疑い**: `clean` や キャッシュ削除は「再現性が消える」ため最初にやらない。原因特定後の最終確認としてなら可
- **Manifest マージ衝突**: `Merged Manifest` ビューまたはエラー中の指示に従い、どのライブラリ由来かを特定する

## 実行時クラッシュ

1. **スタックトレースの確保**: `adb logcat` で `FATAL EXCEPTION` 前後を取得（`adb logcat -b crash` も有効）。本番なら Play Console / Crashlytics のレポート
2. 自アプリのパッケージが出てくる最初のフレームを特定し、該当行を読む
3. 頻出: NPE（null 契約の破れ・lateinit未初期化）/ 状態不正（IllegalState: Fragment/コルーチンのライフサイクス違反）/ プロセス再生成後の未復元状態 / **リリースビルドのみのクラッシュ → R8 の難読化・削除**（keep ルール、mapping.txt でデオブファスケート）
4. 再現手順を最小化してから直す。「直ったはず」ではなく再現手順が通らなくなったことで確認する

## ANR（応答なし)

- 取得: `adb pull /data/anr/` の traces、または Play Console の ANR レポート
- main スレッドが何をしていたかを読む。定番: メインでの同期 I/O・ネットワーク / ロック競合 / BroadcastReceiver 内の重処理
- 予防として StrictMode（debugビルド）でメインスレッド違反を検出する仕込みを提案する

## 「動くはずなのに動かない」系

- ビルドは通るが挙動が変: キャッシュされた古いAPK（アンインストール→再インストール）、複数モジュールの重複クラス、debug/release・フレーバー差分の設定を疑う
- エミュレータ固有: API レベル差・Google Play サービス有無・ハードウェア機能（カメラ等）のエミュレーション限界。実機での再現を確認する
- 特定端末のみ: メーカー独自のタスクキル・権限UI(`android-background`/`android-permissions` 参照)

## 報告形式

原因（証拠のログ・行番号付き）/ 修正内容 / 再現手順での確認結果 / 再発防止（lint・テスト・StrictMode の追加提案）。原因不明のまま症状だけ消した場合は、正直にそう書き、残るリスクを明記する。

## 注意事項

- Stack Overflow 由来の「おまじない」設定を貼らない。効果の説明ができない変更はしない
- `try-catch` で握りつぶして「クラッシュしなくなった」は修正ではない
- ビルド環境の破壊的操作（グローバルキャッシュ削除・SDK再インストール）はユーザーに影響を説明してから
