# Androidアーキテクチャ設計

変更に耐える構造を、プロジェクトの規模に合った複雑さで設計・適用するスキル。

## 大原則

**アーキテクチャは規模に応じて段階的に。** Google 公式の推奨（UIレイヤー + データレイヤー、必要ならドメインレイヤー）をベースに、「今の規模の一段上」までで止める。パターンの適用自体を目的にしない — 判断基準は常に「テストできるか」「変更の影響範囲が閉じるか」。

## 設計の型

### 単方向データフロー（UDF）

```
UI(Compose) --イベント--> ViewModel --> Repository --> DataSource
UI(Compose) <--UiState(StateFlow)-- ViewModel
```

- **UiState は1画面1つの data class** にまとめ、`StateFlow` で公開する（`isLoading`, `items`, `error` をバラバラの State にしない）
- UI からのイベントは ViewModel のメソッド呼び出しに集約。UI にビジネスロジックを書かない
- 一度きりのイベント（トースト・遷移）は UiState に「未消費イベント」として持たせて消費時にクリアするか、慎重に設計する（Channel の乱用は取りこぼしの温床）

### レイヤー責務

- **UI層**: 状態を描画に変換するだけ。Composable は可能な限りステートレス（state hoisting）
- **ViewModel**: UiState の組み立てと画面ロジック。**Android の import（Context 等）を持ち込まない**（テスト不能になる）。構成変更を超えて生存することを前提に、Activity/View への参照を絶対に持たない
- **データ層**: Repository がデータの正を持つ。「オフラインファースト」（DB を真実源にし、ネットは同期役）を基本形として検討する（`android-data` スキル参照)
- **ドメイン層（任意）**: 複数 ViewModel で重複するロジックが出てきたら UseCase として切り出す。最初からは作らない

### DI

- 中規模以上は Hilt。ViewModel・Repository をコンストラクタ注入にし、テストで差し替え可能にする
- 小規模なら手動 DI（Application にファクトリを置く）で十分。Hilt 導入のビルドコスト増と天秤にかける

### モジュール分割

単一モジュールで開始し、以下のシグナルが出てから分割する: ビルド時間が開発を妨げる / チームが領域で分かれる / 機能の境界を強制したい。分割する場合は `core/`（共通）+ `feature/`（画面単位）の型に従う。

## 手順

1. **現状把握**: 既存コードなら構造・依存方向・テストの有無を読み、問題（神クラス、UI内ロジック、双方向依存）を特定する
2. **設計/改善提案**: 上記の型に沿って、規模に合った構成を提案。既存改善はビッグバンリライトでなく「新規画面から新構造 + 触った画面から移行」の段階案を出す
3. **適用**: 1画面ぶんを模範実装し、パターンを示す（全画面一括変換はレビュー不能になるのでしない）
4. **検証**: ビルド + 既存テスト + 対象画面の動作確認。ViewModel のテストが書ける状態になったことをテストを1本書いて証明する

## レビュー観点（レビュー依頼の場合）

- ViewModel に Context / View / Activity 参照がないか
- 画面回転（構成変更）でデータ再取得・状態消失が起きないか
- Flow の collect が生存期間を守っているか（`collectAsStateWithLifecycle` / `repeatOnLifecycle`）
- UiState が複数の真実源に分裂していないか
- Repository を飛ばして DataSource を直接触る抜け道がないか

## 注意事項

- 「正しいアーキテクチャ」の宗教論争を持ち込まない。既存プロジェクトに流儀があるならそれに従い、変更提案は問題ドリブンで
- リファクタリングは動作を変えないことをテストか手動確認で保証してから完了とする
