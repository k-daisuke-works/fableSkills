# Android権限・プライバシー

拒否されても壊れない権限フローと、そもそも権限を要らなくする設計を行うスキル。

## 大原則

**最良の権限は「要求しない」。** 実装の前に、権限なしで済む代替APIを必ず検討する。権限が必要な場合も「拒否されるのが普通」という前提でフローを設計する — 拒否でクラッシュ・機能全損するアプリは設計ミス。

## 手順

### 1. 権限を消せないか検討する

| やりたいこと | 権限不要の代替 |
|---|---|
| 画像・動画を選ばせる | **Photo Picker**（権限ゼロ。まずこれ） |
| ファイルを開く/保存する | Storage Access Framework (`ACTION_OPEN_DOCUMENT` / `CREATE_DOCUMENT`) |
| 自アプリのファイル保存 | アプリ専用領域（`filesDir` 等。権限不要） |
| 写真1枚撮る | `ActivityResultContracts.TakePicture`（カメラアプリ委譲） |
| 位置のおおまかな情報 | 精密でなく `COARSE` だけで足りないか |

代替で済むのに権限要求する実装を見つけたら移行を提案する（審査・ユーザー信頼の両面で得）。

### 2. 権限フローの設計

権限が本当に必要な場合、状態遷移をすべて実装する:

1. **要求前**: 機能の利用文脈で要求する（起動時一括要求は禁じ手）。必要なら要求前に1画面で価値を説明する
2. **shouldShowRequestPermissionRationale = true**: 一度断られている。理由を説明してから再要求
3. **完全拒否（二度と表示しない相当）**: 再ダイアログは出せない。機能を無効化 or 設定アプリへの誘導動線を出す。**この状態の検知と UI を必ず実装する**（最も漏れやすい）
4. **付与後に設定で剥奪**: 戻ってくるたびに権限を再チェックする（キャッシュした判定を信じない）

Compose では `rememberLauncherForActivityResult(RequestPermission())` を使い、状態を UiState に反映する。

### 3. 機微権限の個別注意

- **位置情報**: FINE/COARSE の段階要求、「アプリ使用中のみ」がデフォルト。**バックグラウンド位置情報は別権限+Play審査の追加要件**であり、要件の必然性から確認する
- **カメラ・マイク**: 使用中インジケータが出る前提で、使う瞬間だけアクセスする
- **連絡先・SMS・通話履歴**: Playの制限権限。ほとんどのアプリで代替を探すべき
- Android 14+ の「写真の一部のみ許可」（Selected Photos）状態のハンドリング

### 4. プライバシー対応（実装と申告の整合）

- 収集しているデータの棚卸し（自コード+SDK。広告SDK・分析SDKが何を送るかまで）
- **Play Console のデータセーフティ申告と実装が食い違うと審査落ち・掲載停止**。収集データ一覧を `docs/data-safety.md` に記録し、SDK追加のたびに更新する運用を提案する
- プライバシーポリシーに書くべき項目のリストアップ（ポリシー文面の最終確認は法務・専門家を推奨）

### 5. 検証

- [ ] 各権限の「初回許可 / 初回拒否 / 完全拒否 / 設定で後から剥奪」の4状態すべてで機能が破綻しない
- [ ] 拒否状態での該当機能の UI（無効表示・説明・設定誘導）
- [ ] `adb shell pm revoke` で権限を剥奪しての再現テスト
- [ ] targetSdk 更新で挙動が変わる権限（通知・ストレージ・アラーム等）の回帰確認

## 注意事項

- 権限の要件・Playポリシーは頻繁に変わる。機微権限を扱う際は最新の公式ドキュメントとポリシーを確認してから設計する
- 「あとで使うかもしれない」権限を Manifest に置かない（審査リスク+ユーザー不信）。使わなくなった権限は削除する
- 子ども向けアプリ（ファミリーポリシー対象）は権限・広告の制約が別次元に厳しい。該当するかを最初に確認する
