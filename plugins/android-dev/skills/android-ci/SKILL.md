# Android CI/CD

PRごとの品質ゲートと、再現可能なリリースビルドの自動化を構築するスキル。

## 大原則

**CIの価値は速さと信頼性。** 遅いCI（30分超）や不安定なCI（たまに落ちる）は無視されるようになり、存在しないのと同じになる。ジョブを「PRごとの速い検査」と「重い検査」に分離し、前者を10分以内に保つ設計を目指す。

## 手順

### 1. 現状確認

- CI 基盤（GitHub Actions / GitLab CI / Bitrise 等)の指定。以下は GitHub Actions を例にするが構造は共通
- 既存のワークフロー・Gradle タスク・テストの有無（`android-testing` の資産）
- リリース自動化までやるか、PR 検査までかのスコープ確認

### 2. PR検査ワークフロー（基本形）

トリガー: pull_request。ジョブ構成:

1. **セットアップ**: JDK（プロジェクトの要求版）+ **Gradle キャッシュ**（セットアップ用の公式アクションのキャッシュ機構を必ず有効化。これだけで数分変わる）
2. **静的検査**: `./gradlew lint`（+ detekt / ktlint があれば）。結果を PR に表示する
3. **単体テスト**: `./gradlew testDebugUnitTest`。失敗時にテストレポートをアーティファクト化
4. **ビルド確認**: `./gradlew assembleDebug`

Instrumented テスト（エミュレータ）は重くて不安定になりやすい。導入する場合は nightly か main マージ時に分離し、PR 必須にはしない判断を提案する。

### 3. リリースワークフロー（スコープに含む場合）

トリガー: タグ push か手動（workflow_dispatch）。

- versionCode の自動採番（run number ベース等、単調増加を保証する方式）
- 署名: keystore とパスワードは **Secrets** に（base64 でエンコードして格納→復号）。リポジトリに置かない
- `./gradlew bundleRelease` → AAB をアーティファクト化
- Play への自動アップロード（Gradle Play Publisher か公式 API 経由のアクション + サービスアカウント）は、まず**内部テストトラックへの自動配信**から始める（製品版への完全自動はロールバック不能と組み合わさるとリスク）
- `mapping.txt` の保管・アップロードを忘れずに組み込む

### 4. 品質ゲートの運用設計

- 必須チェック（ブランチ保護）にするジョブを決める。**全部必須は開発を止める** — lint 警告は必須にせず件数の悪化のみ検知する等の段差をつける
- 依存更新の自動化（Renovate / Dependabot）+ CI が通れば安心してマージできる状態を作る
- キャッシュ・並列化・モジュール分割後の `--configuration-cache` 等でCI時間を定期的に見直す

### 5. 検証

- 実際に PR を作って（またはワークフローを手動実行して）全ジョブが通ることを確認する
- わざとテストを壊した状態で「ちゃんと落ちる」ことも確認する（通ることしか確認しないCIは節穴の検証漏れに気づけない）
- 初回実行とキャッシュ有効時の所要時間を報告する

## 注意事項

- ランナーの Android SDK は最初から入っていることが多い（GitHub ホストランナー等）。不要な SDK インストールステップで時間を溶かさない
- Secrets の値をログに echo しない。デバッグ時も伏せ字確認に留める
- CI 専用の裏技設定（CIだけ lint を緩める等）はローカルとの乖離を生む。設定は Gradle 側に一元化し、CI は呼ぶだけにする
- コスト（プライベートリポジトリの分課金）に触れ、無駄な matrix 実行・毎コミット実行を避ける設計にする
