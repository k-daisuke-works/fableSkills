# Androidリリース準備

Google Play に安全に出し、更新し続けられる状態を作るスキル。

## 大原則

**署名鍵の喪失は取り返しがつかない。** アップロード鍵の管理と Play App Signing の理解を最優先で確認する。また、Play の要件（targetSdk・ポリシー）は毎年変わる — このスキルの記述より**最新の公式要件の確認を必ず先に行う**。

## 手順

### 1. リリースビルドの構成

- **署名**: Play App Signing（Google が署名鍵管理、開発者はアップロード鍵）を前提に設定する。keystore は git 管理外(`.gitignore` 確認)+ 安置場所とバックアップをユーザーと確認。CI から署名する場合は署名情報を Secrets 経由に
- **R8**: `minifyEnabled` + `shrinkResources` を有効化し、**リリースビルドでの全機能動作確認**を必須にする（リフレクション・シリアライズ系のクラッシュは R8 有効時のみ出る）。`mapping.txt` を毎リリース保管（クラッシュ解析に必須。Play へのアップロードも設定）
- **ビルド分離**: debug と release で applicationIdSuffix を分ける（共存可能に）、ログ出力・デバッグ機能の release 無効化を確認する
- **バージョニング**: versionCode の採番ルール（単調増加。CI 連番か日付ベース）と versionName の運用を決める
- 形式は **AAB**（`./gradlew bundleRelease`）

### 2. リリース前チェック

- [ ] リリースビルド実機での主要フロー確認（R8 起因の確認を兼ねる）
- [ ] targetSdk が Play の現行要件を満たすか（**要最新確認**）
- [ ] 権限の棚卸し: Manifest の全権限に説明が付くか。不要権限の削除（`android-permissions`）
- [ ] データセーフティ申告と実装の一致（SDK が送るデータ含む）
- [ ] プライバシーポリシー URL の準備（ほぼ全アプリで必須）
- [ ] クラッシュレポート体制（Play Vitals / Crashlytics）が本番で有効か
- [ ] 課金・広告があれば各ポリシー（課金は Play Billing 必須の対象か等）の確認

### 3. ストア掲載

- 掲載素材の一覧を作る: アイコン、フィーチャーグラフィック、スクリーンショット（スマホ必須+タブレット）、短い説明(80字)・詳細説明
- 説明文は `marketing-biz` プラグイン（copywriting）と連携可能。検索キーワードを自然に含め、誇大表現（ランキング操作を疑わせる文言）を避ける
- コンテンツレーティングの質問票は正直に回答する（虚偽は後の掲載停止リスク）

### 4. 公開戦略

- **内部テスト**（即時反映・少人数）→ クローズド → 製品版の段階を使う。最初の審査は日数がかかる前提でスケジュールに織り込む
- 製品版は**段階的公開**（数%から開始）を推奨し、Vitals（クラッシュ率・ANR率）を見て拡大する運用を設計する
- ロールバックはできない（新しい versionCode で修正版を出す）ことを共有し、ホットフィックスの手順を用意する

### 5. 審査リジェクト対応（依頼があれば）

リジェクト理由の文面を精読し、該当ポリシーの原文を確認 → 実装/申告/掲載情報のどこが引っかかったか特定 → 修正と再提出文の作成。よくある原因: データセーフティと実装の不一致、権限の正当性説明不足、メタデータポリシー違反、壊れたログイン（審査用テストアカウントの不備）。

## 注意事項

- 鍵・パスワード・サービスアカウント JSON をリポジトリに置かない。見つけたら即座に指摘し、ローテーションを推奨する
- 「審査を通すための一時的な機能隠し」等の偽装は提案しない（発覚時はアカウント停止級のリスク)
- 初回リリースは最小構成で早く出し、Vitals とレビューを見ながら育てる方針を推奨する
